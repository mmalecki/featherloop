# Harness bench, prompt and advisor runs on a G4 (2026-10-04/05)

featherloop alone, on the 9B hard set, to compare system prompts and advisor tool
descriptions, now on a faster GPU and budgeted by output tokens rather than wall clock.
Raw results are in `test/harness-bench/results/g4-*` (not in git); each run's `summary.md`
and `analysis.md`, and `g4-hard-9b-ABC.analysis.md` comparing the prompts, are in `2026-10-05/`.

## Setup

- **Cases:** the 9B hard set from the first round: 19 cases the 9B failed at least once,
  3 reps each (57 runs per arm).
- **Model:** Qwen3.5 9B Q5_K_M, llama.cpp b11371, on a spot `g4-standard-48` (RTX PRO 6000,
  96 GB): 8 slots, unified KV of 1M tokens, speculative decoding (MTP, 2 drafts).
- **Budget:** `--max-output 40000` generated tokens per run, with a 60-minute timeout as
  a safety net that no run hit. 40k cut none of the first round's 304 9B passes (the
  most any used was 36.6k).
- **Code:** `latest` at the merge of the first round, which adds the repeat-output sensor
  and the background shell to featherloop, so first prompts and shell results differ
  from the first round. Compare these arms with each other, not with the first round.
- **Arms:** run at the same time on the same server, 2 runs at a time each.
  - **A:** `latest`.
  - **B:** `agentic-prompt`, "Work in a loop: take a step with your tools, check what it
    did, and repeat until the task is done. Settle doubts by trying things, not by long
    deliberation."
  - **C:** `check-prompt`, "Use your tools to check your work and your knowledge, rather
    than reasoning at length."
  - **D0/D1:** `featherloop-advisor` with Sonnet 5.5 as the advisor, on the 6 hard cases
    where the 9B got stuck iterating: D0 with the stock advisor description, D1 with
    "when stuck" spelled out (`advisor-triggers`: "the same tests failing twice in a row,
    or a command's output saying \"[Same output as …]\""). Stopped at half, 9 runs each,
    once neither had called the advisor.

## Results

### Prompts

| | A: stock | B: work in a loop | C: check with tools |
|---|---:|---:|---:|
| Passed | 24/57 (42%) | 25/57 (44%) | 29/57 (51%) |
| 95% interval | 30–55% | 32–57% | 38–63% |
| Out of budget: runaway response | 14 | 12 | **6** |
| Out of budget: iterating | 18 | 20 | 22 |
| Mean partial credit of runs out of budget | 60% | 61% | 61% |
| Output tokens / run | 19.6k | 20.7k | 21.7k |
| Tokens / pass (in + out) | 1084k | 1174k | **1038k** |
| Tool calls / run | 18.0 | 19.1 | 19.9 |

B's 25 includes one run whose tests all passed when the budget stopped it.

**No prompt wins significantly.** Head to head on the cases where exactly one arm passed,
C beats A 9 to 4 (sign test p = 0.27), and C beats B 7 to 3 (p = 0.34). A and B are tied
(8 to 7). Reps vary a lot: the same case often passes once and fails twice in one arm.

**C cuts runaways the most.** A response that reasons until the budget runs out, 57–200k
characters, most with 70–99% of their lines repeating earlier ones, ended 14 of A's runs,
12 of B's, and 6 of C's. C's runs instead iterate more: more test runs per run (4.2 vs
3.6), less reasoning after failing tests (median 2.0k characters vs 3.1k). That's the
behaviour the prompt asks for. It turns some runaways into passes, and others into
iterating until the budget runs out.

**B doesn't repeat its first-round lead.** In the first round, on L4s with a 30-minute
timeout, B passed 28 to A's 24 and halved runaways. Here it's 25 to 24, with 12 runaways
to 14. The changes since (the repeat sensor, a budget in tokens instead of minutes)
make the rounds not directly comparable, and with 57 runs per arm a 4-run difference is
within noise either way.

### The advisor

| | Runs | Passed | Advisor calls | Cost |
|---|---:|---:|---:|---:|
| D0: stock description | 9 | 3 | 0 | $0 |
| D1: "stuck" spelled out | 9 | 0 | 0 | $0 |

**The 9B never asked for advice.** Not even when the triggers D1 names happened in plain
sight: 9 or 10 tests failing four and seven times in a row on `pov`, and `react` stuck at
13 of 14 in run after run. Saying when to ask in the tool's description
doesn't get a 9B to ask. D1 passing nothing against D0's 3 is most likely chance (one
sentence differs, in a tool the model never used), but worth watching in later variants.

The repeat sensor has a gap that weakened D1's second trigger: it only normalises
timings and escape codes, so Python test failures that print objects
(`<pov.Tree object at 0x7ef16deab1d0>`, a new address each run) never repeat. Fixed on
`repeat-addresses`, not used in these runs.

## Infrastructure

- **A full shared KV cache fails runs mid-response.** The first attempt ran on 262k of
  unified KV across 8 slots; 6 runs at 40–60k filled it, and llama.cpp failed every
  slot at once with "Context size has been exceeded", inside a 200 response. The bench
  graded those runs as plain failures. Now the proxy records errors in a stream and counts
  them as infrastructure errors (`bench-stream-errors`), and the server runs with 1M of
  KV. The first 7 results were discarded.
- **Throughput.** About 250–280 output tokens/s across 7–8 runs, around 33 tokens/s per
  run at the 50–100k contexts these runs reach (172 tokens/s for one fresh run). Per-run
  speed didn't change between 6 and 8 runs at once, so the GPU wasn't saturated (about
  45–65% busy). The server's main thread sat at 100% of one core, which may be CUDA's
  spin-wait rather than a CPU limit. Comparing with and without speculative decoding is
  the next check.
- **Spot preemption** didn't happen. `bench-server-pool` (a sketch, not yet run against
  real servers) lets runs pull from a pool of servers listed by a GCP managed instance
  group, and requeues the runs of a server that drops out.
- **Wall clock:** 6 hours for the three prompt arms (18:43–00:32 UTC), against an
  estimate of 2.5–3.5; half the runs used their full 40k budget.

## Server settings

Measured afterwards on the same idle server with `2026-10-05/throughput-probe.py`: fixed
1,500-token outputs (`ignore_eos`), the server's sampling, 1M unified KV.

| | no speculation | speculation (draft-mtp, 2) | flash attention forced on |
|---|---:|---:|---:|
| 1 request, short prompt | 171 tok/s | **228** (+33%) | 172 |
| 8 requests, short prompts, total | **711** | 677 (−5%) | 711 |
| 8 requests, 60k-token prompts, each | 16.3 | 16.4 | 16.3 |
| 8 requests, 60k-token prompts, wall | **191 s** | 212 s (+11%) | 191 s |

- **Speculative decoding** only pays for a lone request; with 8 at once verifying drafts
  costs more than it saves. Benches should run without it.
- **Flash attention** is already on by default.
- **Long contexts set the pace.** 8 requests at 60k get about 16 tokens/s each, about 130
  in total, against about 138 for one alone at 56k: every new token reads the whole KV,
  so running more at once adds nearly nothing, where short contexts gain 4× from 8 at
  once. More GPUs (a server each) or shorter contexts help; more slots on one GPU don't.
- The server now runs with `-c 1048576` and without speculation. The VM's saved start
  command had `-c 262144` and speculation on.

## A 4B on CPU

Spark-X2.5-4B (Q8_0, llama.cpp b11382) on the same VM's CPU, 3 easy cases at a time:
tool calls parse fine (with a system prompt; without one it once made up a directory
listing instead of calling a tool), but it generates about 11 tokens/s per run with 3 at
a time, and reasons for 10–20k tokens at a time. All 3 runs timed out at 30 minutes;
`robot-name` had a passing solution but spent 16 shell calls debugging Python object ids
in its own probing script. Usable only with thinking off or capped, or on a GPU.

## Next

- **Prompts:** C is the lead to iterate on. Its remaining failures are iterating until the
  budget runs out, not runaways.
- **Advisor:** stop relying on the model to ask. Either the repeat note itself suggests
  the advisor at that moment, or the loop calls it at fixed points. The latter is
  tomorrow's experiment: a 35B-A3B with advisor breakpoints at planning and review, priced
  against hosted models solo (Haiku solo, about $0.03 a run on the quick set, is the bar).
- **Server:** checked, see Server settings: no speculation, 1M KV; scale with GPUs.
- **Merge:** `bench-stream-errors` (stream errors, runaway analysis), `repeat-addresses`,
  and `bench-server-pool` after a real two-server run.
