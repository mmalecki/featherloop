# Harness bench, a user-role nudge at the repeat signal (2026-10-07/08)

featherloop alone, on the 9B's informative hard cases, with the presence penalty on: when
the repeat sensor says a command's output repeats, does a message from the user at that
moment change what the model does, and does it help? Raw results are in
`gs://mm-llm-8deefb51-bench/results/2026-10-07-g4-hard-9b-mid-{A,N}` (not in git); each arm's
`summary.md` and `analysis.md`, and `g4-hard-9b-mid-AN.analysis.md` comparing them, are in
`2026-10-07/`.

## Setup

- **Cases:** `--set hard-9b-mid`, the 9 cases of `hard-9b` that passed neither nearly always
  nor never on 2026-10-06, 10 reps each (90 runs per arm).
- **Model:** Qwen3.5 9B Q5_K_M, llama.cpp b11371, three spot `g4-standard-48` (`-c 393216
  -np 5 --kv-unified`), server default `--presence-penalty 1.5`; `-m qwen3.5-9b`, which now
  sends `presence_penalty: 1.5` itself.
- **Budget:** `--max-output 40000`, timeout 120 minutes (none hit).
- **Arms**, run together (23:16–01:49 UTC), `-j 2` each, 12 runs at once:
  - **A:** `latest` (6051ea1).
  - **N:** `nudge-on-repeat` (fc6fdc7): when a tool result carries the repeat sensor's note
    (`[Same output as …]`), the loop sends, as the user, before the next turn: "You've run
    this before and got the same result: it isn't working. Before your next command, say
    what you expected, what you got, and what you'll do differently." Generic on purpose:
    on 2026-10-06 only 54% of repeats were test runs, the rest the model's own probe scripts.
- **Readouts, set before the run:** first the behaviour (does the nudge fire, and do runs
  repeat less), then test score (the share of tests passing at the end; two identical arms
  of 90 land within ±5.6 points of each other), then passes. Comparisons are stratified
  permutation tests: runs shuffled between the arms within each case.

## Results

| | A | N: nudge | p |
|---|---:|---:|---:|
| Nudges / run | 0 | 1.3 | |
| Repeat notes / run | 3.02 | **1.30** | **0.005** |
| Same command again within 3 shell calls of a note | 54% | 38% | |
| Requests / run | 41 | 36 | 0.12 |
| Tokens / run (prompt + completion) | 1238k | **922k** | **0.008** |
| Completion tokens / run | 26.8k | 28.5k | 0.30 |
| Peak context, median | 50k | 42k | |
| Passed | 51/90 (57%) | 47/90 (52%) | 0.61 |
| Test score | 87% | 85% | 0.71 |
| Runaway responses | 2 | 2 | |
| API errors | 0 | 0 | |

**The model acts on a message from the user where it ignored the same signal in a tool
result.** With the note alone (A), runs hit a repeat 3.0 times each, and after one ran the
same command again 54% of the time. With the nudge they hit 1.3 (p = 0.005), and ran it
again 38% of the time. The 9B never asked for the advisor on 2026-10-05, and never acted on
the note: an instruction in the user's turn, at the moment it's stuck, is what it follows.
The nudge says more than the note, so this shows the instruction works, not the channel
alone.

**It doesn't help the model pass.** 47 against 51 passes, 85% against 87% of tests: both
within noise. Like the edit line on 2026-10-06 (fewer rewrites then, fewer repeats now), it
changes what the model does and not what it gets right. Where the 9B is stuck it
lacks the idea, not the method: a better-behaved loop over the same idea ends the same way.

**It makes runs cheaper.** A quarter fewer tokens a run (922k against 1238k, p = 0.008),
from fewer requests over smaller contexts: less re-running of what didn't work. Completion
tokens are about the same (the model now says what it expected and got). On llama.cpp most
of the saving is cached prompt; on a hosted API, where cached prompt is billed, it's a
quarter off the bill at the same score.

## Infrastructure

- Three servers, 180 runs: no API errors, requeues, refusals, lost servers or timeouts;
  5–9 requests resent per arm after closed connections.
- Results synced to the bucket as they came; the instance group was resized to 0 at
  01:49 UTC, when the run drained.

## Next

- **Keep the nudge, for cost:** a quarter fewer tokens at the same score. Land
  `nudge-on-repeat` (after MCP, rebased), with the wording as tested.
- **The channel is settled, so the advisor can use it.** When the repeat sensor fires, the
  harness asks a stronger model (Sonnet) with the task, the code and the last test output,
  and puts its answer in the user's turn, as the nudge was. That brings what the 9B lacks
  where it's stuck: the idea. About 1.3 triggers a run, a few cents each; ask first.
- Or the other way to more ideas: the 35B-A3B on `hard-9b-mid`, with the penalty and the nudge.
