# Harness bench, presence penalty and prompt lines on a G4 pool (2026-10-06)

featherloop alone, on the 9B hard set, with Qwen's presence penalty on: does it remove the
runaway responses the earlier prompt lines were fighting, and does a prompt line help with
what's left? Raw results are in `gs://mm-llm-8deefb51-bench/results/2026-10-06-g4-hard-9b-presence-*`
(also not in git); each arm's `summary.md` and `analysis.md`, and
`g4-hard-9b-presence-ACD.analysis.md` comparing them, are in `2026-10-06/`.

## Setup

- **Cases:** `--set hard-9b`, the 19 cases of the second round, 3 reps each (57 runs per arm).
- **Model:** Qwen3.5 9B Q5_K_M, llama.cpp b11371 (image pinned), on a pool of three spot
  `g4-standard-48` (the managed instance group `qwen3-5-9b`): `-c 393216 -np 5 --kv-unified`,
  no speculative decoding, server sampling at its defaults (temperature 0.6, top-k 20,
  top-p 0.95, presence penalty 0).
- **Sampling:** every arm runs `-m qwen3.5-9b-presence`: featherloop sends `presence_penalty: 1.5`,
  Qwen's setting against circular thinking.
- **Budget:** `--max-output 40000`, timeout 120 minutes (none hit).
- **Pool:** two arms at a time, `-j 2` each: 4 runs per server, 12 at once.
- **Code:** `bench-iterating` (the server pool, the integrity fixes, the Iterating analysis).
- **Arms**, each one line under the stock `Concise assistant. Today is … cwd: …`:
  - **A:** none.
  - **C:** "Use your tools to check your work and your knowledge, rather than reasoning at length."
  - **D1:** "Change code with update, a few lines at a time, and keep what already passes; don't rewrite whole files."
  - **D2:** "Run the tests without head or tail: the failures and the summary are in the full output."
- A and C ran together (01:28–02:50 UTC), then D1 and D2 (02:58–04:20).

## Results

| | A | C | D1: edit | D2: full output |
|---|---:|---:|---:|---:|
| Passed | 34/57 (60%) | 32/57 (56%) | 29/57 (51%) | 33/57 (58%) |
| 95% interval | 47–71% | 43–68% | 38–63% | 45–70% |
| Runaway responses | 0 | 0 | 0 | 0 |
| Out of budget, iterating | 23 | 24 | 28 | 24 |
| Whole-file rewrites / run | 8.8 | 9.3 | **6.7** | 10.5 |
| `update` calls (all runs) | 34 | – | **343** | – |
| Test commands cut by head/tail | 53% | 56% | 58% | 59% |
| Tokens / pass | 1305k | 1561k | 2024k | 1458k |
| API errors | 0 | 0 | 0 | 0 |

No pair differs significantly (A vs C 7–5, p = 0.77; A vs D1 10–5, p = 0.30; A vs D2 9–8, p = 1.0).

**The presence penalty ended runaway responses.** None in 228 runs. Without it, in the
second round, 14 of A's 57 runs and 6 of C's ended in one response reasoning until the budget
ran out. With them gone, C's line no longer helps (34 vs 32): it was fighting a sampling
problem. Every failure is now the model iterating until the budget runs out.

**Against the second round,** case by case, A and C together passed 66 of 114 against 53
(10 cases better, 3 worse, sign test p = 0.09). That round also had speculative decoding on,
8 slots, 1M of KV and older bench code, so this isn't the penalty alone; the runaways are.

**D1 changed what the model does, and passes didn't follow.** Told to edit, it called
`update` ten times as often (343 vs 34; 11% of them failed) and rewrote whole files a quarter
less (6.7 vs 8.8 a run), but passed 29 to A's 34, at 2024k tokens a pass (many small edits,
each re-reading a growing context). Losing progress to rewrites isn't what keeps the 9B
from passing.

**D2 didn't change what the model does.** It still cut 59% of its test commands with
`head` (A: 53%; `head -60` to `-100`, though the task says plainly how to run the tests and
the shell tool already keeps the end of long output). A reworded line wasn't worth an arm:
in A's 10 runs that ended with all but 1–3 tests passing, the last test command wasn't cut
in 7, so its whole output was in view; the 3 runs read by hand had the failing test's
assertion in front of the model (`AssertionError: 5160 != 5120`), one of them with the
repeat sensor's `[Same output as 13 runs ago]` and already running only that one test.
Where it's stuck, it sees what's wrong and can't fix it.

## Cost of iterating

Tokens per run rose from 457k (second round's A) to 778k, nearly all of it prompt: A's runs
read 43M prompt tokens (98% from the cache) and wrote 1.4M. A runaway ends a run in one long
response; iterating makes about 29 requests a run at a median peak context of 45k, each
re-reading what came before. On llama.cpp cached prompt is cheap; on a hosted API it's
billed (at a tenth of input for Haiku), which matters for the 35B-vs-Haiku comparison.

## Infrastructure

- **The pool held.** Three servers, two benches at a time, 228 runs: no API errors, no
  requeues, no server refused or lost, no timeouts; 66–86 runs on each server.
- **Resends work.** The proxy resent 3–8 requests per arm after a kept-alive connection the
  server had closed; each would otherwise have failed a request and requeued its run.
- **Results left the box as they came:** `--sync-cmd` to the bucket, every 5 minutes and at
  the end.
- The instance group was resized to 0 at 04:26 UTC, when the prompt ideas ran out.

## Next

- **No more system-prompt lines for the 9B on this set.** Seven arms over two rounds; none
  moved passes beyond noise. The one lever that did was sampling.
- **Make the presence penalty the default** for Qwen in the bench's configs (and featherloop's
  docs), and rerun the quick and full sets with it.
- **Where the model is stuck, it knows it's stuck** (the repeat sensor fires) and still can't
  get unstuck: that's the moment for a harness-triggered advisor call, not a model-chosen one.
  It costs Sonnet tokens: ask first.
- The reasoning budget is moot now: with the penalty, A's reasoning is 432 characters a
  response (median), 3.1k at p90, none over 20k; an 8k cap would cut nothing. The lever
  still untried is a bigger model (the 35B-A3B) on the same set.
