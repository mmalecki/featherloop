# Harness bench, first round (2026-10-03/04)

featherloop against opencode (stock, and with the user's agents for smaller models),
nanocode, and on some runs Claude Code, all on the same models, measured from the wire.
Raw results are in `test/harness-bench/results/` (not in git), one directory per run;
each run's `summary.md` and `analysis.md`, and the A/B/C comparisons, are in `2026-10-04/`.

## Setup

- **Cases:** Aider Polyglot, Python and JavaScript, 82 exercises (`all`), or 30 easier ones
  (`quick`). Tests visible to the agent, which runs them itself; graded on the shipped tests.
- **Models:** Qwen3.5 9B and Qwen3.6 35B A3B (Q5_K_M, llama.cpp b11371, 4 slots, unified KV,
  262k context, speculative decoding) on single-L4 VMs; Claude Haiku 4.5 on the API.
- **Runs:** one rep per case, 4 at a time, 30-minute wall-clock timeout; infrastructure
  failures (server crashes, proxy timeouts) rerun.
- **Harness settings:** opencode's title agent off; opencode-custom without websearch;
  featherloop `--shell`, no advisor; nanocode at its stock 8192 output tokens (later runs
  give it the model's limit).

## Results

### Qwen3.5 9B, all 82 cases

| | featherloop | opencode-stock | opencode-custom | nanocode |
|---|---:|---:|---:|---:|
| Passed | 57/82 (70%) | 65/82 (79%) | 58/82 (71%) | 62/82 (76%) |
| 95% interval | 59–78% | 69–87% | 60–79% | 65–84% |
| Timeouts | 24 | 18 | 24 | 7 |
| Tokens / run | **165k** | 321k | 368k | 239k |
| Tokens / pass | **237k** | 404k | 521k | 316k |
| First prompt | 1.5k | 5.7k | 4.2k | 1.3k |
| Peak context, median | **10k** | 18k | 17k | 13k |

No pairwise pass-rate difference is significant (featherloop vs opencode-stock: 6 cases
to 14, p≈0.12). featherloop uses half or less of opencode's tokens per pass.

### Qwen3.6 35B A3B, all 82 cases

| | featherloop | opencode-stock | opencode-custom | nanocode |
|---|---:|---:|---:|---:|
| Passed | 77/82 (94%) | 78/82 (95%) | 81/82 (99%) | 58/82 (71%) |
| Tokens / run | 87k | 69k | 86k | 34k |
| Tokens / pass | 92k | 72k | 87k | 48k |
| First prompt | 1.5k | 5.7k | 4.2k | 1.3k |
| Output cut off at limit | 0 | 0 | 0 | 23 |

The three uncapped harnesses tie. featherloop generates more output here (8.2k completion
tokens per run against opencode's 5.2k), which outweighs its smaller prompt. nanocode's
stock 8192-token cap cuts the 35B's longer reasoning off mid-thought: 23 of its 24 failures.

### Claude Haiku 4.5, quick set (30 cases), with dollar costs

| | featherloop | opencode-stock | opencode-custom | nanocode |
|---|---:|---:|---:|---:|
| Passed | 30/30 | 30/30 | 30/30 | 29/30 |
| Tokens / run | **42k** | 99k | 94k | 65k |
| Prompt read from cache | 61% | 86% | 87% | 0% |
| Cost / run | **$0.030** | $0.038 | $0.035 | $0.074 |

Total $5.31. Prompt caching narrows featherloop's 2.3× token advantage to 15–25% in
dollars: Haiku caches nothing under 4096 tokens, and featherloop's early requests are
smaller than that. nanocode asks for no caching and costs 2.5× as much. Its one failure
was a `glob` that followed `node_modules` into a 1.5 MB request, over the context.

### Claude Code on the 9B, quick set

28/30 passed, at 261k tokens per run (4.4× featherloop) and a 16k-token first prompt
(30k on Haiku, where it also turns extended thinking on). On llama.cpp it needs one
compatibility fold (a mid-conversation system message moved into the user turn).

## Why runs fail

Almost every failure is a timeout, not a wrong answer. Two kinds:

- **Runaway responses:** a single response that reasons for the whole 30 minutes,
  mostly repeating itself (65–96% of its reasoning lines repeat). Often right after a
  failing test, sometimes before any code is written (connect, bowling).
- **Iterating to the timeout:** the model keeps editing and testing without converging,
  e.g. python/forth stuck at 47/54 tests in all three runs.

featherloop elicits more reasoning per response than opencode (2.5–4× the median), and,
like nanocode, gives the model no method; nanocode's output cap is the only thing that
stops its runaways, which is why it has the fewest timeouts on the 9B.

## Prompt experiments (hard sets, 3 reps, featherloop only)

- **B:** "Work in a loop: take a step with your tools, check what it did, and repeat
  until the task is done. Settle doubts by trying things, not by long deliberation."
- **C:** "Use your tools to check your work and your knowledge, rather than reasoning at length."

| | A (original) | B | C |
|---|---:|---:|---:|
| 35B hard set (8 cases) | 17/24 | 19/24 | 16/24 |
| 9B hard set (19 cases) | 24/57 | 28/57 | 11/23 (partial) |
| 9B runaway timeouts | 16 | 9 | 3 of 23 |

On the 35B nothing changes (p 0.5–1.0). On the 9B, B halves runaways and reasoning per
response, and the model acts more (20 requests per run against 16), but most former
runaways become iterating timeouts: +4 passes, not significant (p≈0.39). C looks like B
on the runs it finished. Its 9B run stopped short: four long conversations at once crashed
llama.cpp, repeatedly, on two machines (below). The hard sets also showed regression to
the mean: cases featherloop failed once pass 42–71% of the time on fresh runs.

## Advisor

On python/connect, with Sonnet 5.5 as advisor, the 9B never asked: 15 requests, stuck at
6/10 tests, 30 minutes, no call. The tool's "when stuck" isn't a signal a 9B acts on.

## Integrity

- No run reached the bench's copy of the reference solutions; web use was nil but for one
  `curl` of Exercism's test data.
- One run hardcoded answers from the visible tests (35B, opencode-stock, zebra-puzzle);
  now flagged by `guards.ts`.
- No unparsed tool calls on any model; one hallucinated tool name (Haiku, opencode-custom).

## Infrastructure

- squid's 15-minute read timeout cut nanocode's non-streaming requests (504s): the proxy
  now streams them upstream.
- llama.cpp crashed five times (01:45 and 15:50 on one 9B, 10:17, 11:37, 14:06 on another),
  each time with four ~60k-token conversations generating at once; a 393k unified cache
  didn't help. Probably GPU memory outside the KV cache on the L4, or a llama.cpp bug.
- Wall-clock timeouts make results depend on hardware and load; see `--max-output`.

## Next
